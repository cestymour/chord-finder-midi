# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

InstantChordBT: a React 19 + Vite PWA that identifies the chord being played on a MIDI keyboard, connected either by cable/OS-level MIDI (Web MIDI API) or directly over Bluetooth LE (Web Bluetooth API). Plain JavaScript (no TypeScript), Vitest unit tests, no router, no state library. The UI is available in French (default), English, German and Spanish; most code comments are in French.

## Commands

```bash
npm install        # .npmrc sets legacy-peer-deps=true (added so the CI npm install succeeds)
npm run dev        # Vite dev server, served at base "/"
npm run build      # Production build to dist/, base "/chord-finder-midi/"
npm run preview    # Serve the production build
npm run lint       # ESLint (flat config, eslint.config.js)
npm test           # Vitest unit tests (src/*.test.js), also run by CI before the build
npx vitest run src/chords.test.js   # a single test file
```

Tests cover the React-free modules: `chords.js` (spelling, detection rules, and a round trip over every template × 12 roots × every inversion, with and without incomplete chords), `i18n.js` (every key and chord type in all four languages, note-name conventions), `midiMessages.js`, `explorerLayout.js` (every template placed exactly once), the BLE packet decoding and error codes of `useBluetoothMIDI.js`, and the sample mapping of `pianoSound.js`. React components and the Bluetooth connection flow are not unit-tested. Run with Node 24 (`.nvmrc`). Web MIDI and Web Bluetooth only work in Chromium-based browsers and need a secure context (localhost or HTTPS).

## Deployment

Pushing to `main` triggers `.github/workflows/deploy.yml`, which builds with the Node version from `.nvmrc` (24) and deploys `dist/` to GitHub Pages. The service worker (vite-plugin-pwa, `generateSW`) precaches the app shell, and `workbox.runtimeCaching` caches the Google Fonts (imported at the top of `App.css`) for offline use. The `base` path in `vite.config.js` switches on `NODE_ENV` (`/chord-finder-midi/` in production), and the PWA manifest `scope`/`start_url` reuse it, so renaming the repo means updating that value. The PWA manifest (name, icons, theme colors) is also defined in `vite.config.js`; icon files live in `public/`.

## Architecture

UI, hooks and components are in `src/App.jsx`. The chord engine (templates, detection, explorer voicings) is a pure, React-free module in `src/chords.js`, so it can be imported from plain Node for quick checks. All translations live in `src/i18n.js` (it imports `./chords.js` with the extension so it can be loaded from Node too). The BLE transport is in `src/useBluetoothMIDI.js`. The piano sound is in `src/pianoSound.js`: Salamander Grand Piano samples (Alexander Holm, CC-BY 3.0, credited behind the ⓘ of the Sound setting, `settings.soundHint` plus a link `PIANO_SAMPLES_URL`, and in the README) in `public/piano/<midi>.mp3`, one every 3 semitones from 21 to 108 (mono, 48 kb/s, shortened to 3–6 s with a fade), each note played from the nearest sample with `playbackRate` (at most ±1 semitone). `setPianoSoundEnabled(true)` (on launch when sound is on) fetches and decodes them through an `OfflineAudioContext`, so no user gesture is needed; a note whose sample isn't decoded yet stays silent (its key still lights up). There is no synthesized fallback. The service worker precaches the samples (`workbox.globPatterns` includes `mp3`). To regenerate them, re-encode the Salamander files with ffmpeg (`-ac 1 -b:a 48k`, trim + fade). Playback: the virtual keyboard plays a note when a key goes down and damps it when it goes up, the dictionary plays each chosen chord as an arpeggio (`playPianoArpeggio`), except that tapping the same chord again (same root, type and inversion) alternates block chord (`playPianoChord`) on even taps and arpeggio on odd ones (`exploreRepeatRef` counts consecutive taps), and notes from the real piano are never synthesized (the real piano is heard).

**Note input: two parallel sources feeding the same state.** `ChordIdentifier` (the main component) owns a `Set` of pressed MIDI note numbers and exposes `handleNoteOn`/`handleNoteOff`. Both input hooks call them:
- `useMIDI` (in `App.jsx`) uses `navigator.requestMIDIAccess`, attaches `onmidimessage` to every connected input except virtual "Through" ports, and re-attaches on `onstatechange`. It only requests access on its own when `navigator.permissions.query({ name: "midi" })` says `granted` (it follows `onchange`); otherwise the status is `prompt` and `requestAccess()` (the "Autoriser le câble USB" button in the USB popup of the connect screen) asks on a user gesture. A dismissed prompt goes back to `prompt`, a refusal to `denied`. It returns `{ status, devices, requestAccess }`: status is `pending | prompt | connected | disconnected | denied | unsupported`, devices the input names. This covers USB pianos (on Android through a USB OTG adapter) and Bluetooth pianos paired at OS level; Web MIDI can't tell the two apart.
- `useBluetoothMIDI` connects to the standard BLE MIDI service/characteristic UUIDs, subscribes to notifications, and decodes packets with `ble-midi-parser`. This direct decoding exists because some platforms (notably Windows Chrome) don't expose a BLE MIDI device as a Web MIDI port. The logic lives in a React-free `createBluetoothController`; every action bumps `ctx.attempt` so stale async work gives up. Statuses: `idle | scanning | connecting | connected | reconnecting | lost | error | unsupported`. `ctx.target` is the device currently wanted: a superseded `openLink` closes GATT unless the newer action targets the same device, and a failed open closes it too, so the piano is never left connected with nobody listening. An unrequested GATT disconnect starts an automatic reconnect on the same device (about 20 s, then `lost`). The last device stays known (`btKnownDevice`) after a loss or a manual disconnect, so `reconnectBluetooth` reconnects without the picker. Its id is saved in `localStorage` (`instantchordbt.bluetoothDevice`), and on launch `navigator.bluetooth.getDevices()`, where available, restores it. Such a restored device (`ctx.restored`, until its first successful connection) often refuses `gatt.connect()` until the browser has seen it advertise: only when that first open fails, `connect` waits up to 10 s for an `advertisementreceived` event (`watchAdvertisements`, aborted by any newer action) and retries once. The normal path is unchanged. `btError` is a code (`cancelled | adapterOff | denied | failed`) translated as `bt.error.<code>`. A cancelled picker is shown as a hint, not an error.

**Screens.** `mode` is `"midi"` (tab "Notes → Accord") or `"explore"` (tab "Accord → Notes"), chosen in the segmented `TopBar` (exactly one tab is always active). The arrow labels name the direction so they make sense without context; each tab also has a spelled-out `aria-label` (`tabs.<key>.aria`) so screen readers don't read "right arrow". The app always starts on Piano: connecting a real piano is the app's main purpose. The on-screen keyboard is a fallback, so it stays hidden until it is needed.
- `"midi"` (the Piano screen, tab "Notes → Accord"): the real piano and the on-screen `VirtualKeyboard` share this screen. The keyboard shows only when a piano is connected (BLE or Web MIDI, including while BLE is `reconnecting`, so a short drop doesn't bring the connect screen back) or after the user taps "Piano virtuel" on the connect screen (`keyboardChosen`, not saved). The keyboard keeps its own `virtualNotes` set (click toggles a key), so hardware note-offs can't release clicked keys. The chord is computed from the union of piano and clicked notes, and a piano note-on clears the clicked keys so the two sources don't mix. The keyboard lights both, and scrolls to the piano notes only. When the keyboard was chosen without a piano, `ConnectionStatus` shows a neutral "Piano virtuel" state (never a MIDI error) and a "Connecter un piano" button that hides the keyboard and brings the connect screen back. `virtualNotesRef` is updated together with the state on every change, so quick taps before a render each start from the latest set.
- `"explore"` (the dictionary, tab "Accord → Notes"): the reverse direction. The compact chord card and the root chips (no title, `aria-label` only; 6 per row, 12 in one row in short landscape) stay at the top; all chips are at least 36 px high and have the home buttons' dim green outline (`--accent-line`); in portrait `.display-area--explore` tightens the space around the chord card; root chips use 1.2rem (capped by `2.6vw` in short landscape), type chips stay 0.7rem; only `.explorer__scroll` (the chord types) scrolls, in portrait and in short landscape. The types are two aligned 6-column grids defined in `src/explorerLayout.js`: `MATRIX_ROWS` (quality rows such as M, add, m, dom, sus4, dim, aug, no3 × highest extension: triad, 6, 7, 9, 11, 13, headers translated with `explorer.triad` and the ordinal pattern `explorer.nth`), and `ALTERED_ROWS` (base 7th chord × alteration ♭5 ♯5 ♭9 ♯9 ♯11 ♭13), in a `<details>` closed by default unless the chosen chord is altered. Every template suffix sits in exactly one cell (checked by `explorerLayout.test.js`), so a new template in `chords.js` must also be placed there. Buttons show the suffix only (`M` for the empty major suffix, full type name in `aria-label`/`title`); empty cells are a small dot. `ChordExplorer` picks a root and a template; `buildChordVoicing` turns it into concrete keys, shown read-only on the keyboard (only the voicing keys are lit). "Renverser" cycles inversions (see Explorer voicings).

**Desktop layout.** Everything for computers lives in one block at the end of `App.css`, under `@media (min-width: 900px) and (min-height: 561px)` (`DESKTOP_QUERY` in `App.jsx` must match it), so phones in portrait and in short landscape are untouched. The app is as wide as the full keyboard (52 white keys × 24 px, `--desk-kb-width`), and the keyboard is shown whole and centered (it scrolls only in a narrower window). Above it, the portrait layout sits in a centered 960 px column (`--desk-col`, applied as `padding-inline` so backgrounds stay full width; a `.top-bar::before` spacer as wide as the gear centers the tabs, so their split lines up with the halves below). The primary card takes the left half and the alternatives the right half; with no alternatives the card is centered (`:not(:has(> .secondary-chords))`). On the explore screen `.display-area--explore` is a grid and `.explorer` is `display: contents`: chord card | roots (2 rows of 6) on top, then both type grids side by side, equal width and aligned with the card and roots above (same 20 px gap, divider in its middle), the only part that scrolls. The altered grid is always open there (`ChordExplorer` forces `open` through `useMediaQuery(DESKTOP_QUERY)`, its summary is hidden), and each grid gets a title (`.explorer-grid-title`, hidden on mobile): `explorer.main` (« Classiques ») and `explorer.altered`.

**Virtual keyboard.** A full 88-key piano (MIDI 21–108) inside a horizontal scroller. The key track width is set from `--vk-white-keys` (52) so that 14 white keys (2 octaves) are visible in portrait and 21 (3 octaves) in landscape on desktop. On a phone on its side (short landscape) the white key keeps its portrait width (`(100vh - 24px) / 14`, clamped 22–32 px), so more keys show instead of wider ones. On mount it scrolls instantly so MIDI 48 is at the left. Key positions are percentages from `VK_KEY_SPANS`. `useScrollIntoView` smooth-scrolls (respecting `prefers-reduced-motion`) to put the lowest note at the left only when part of the given notes is hidden: the explorer voicing, or the notes played on the piano (high notes of a wide chord may stay hidden). Notes outside the 88 keys are ignored.

Both hooks decode MIDI with the shared `dispatchMidiMessage` (`src/midiMessages.js`): `0x90` with velocity > 0 is note on; `0x80`, or `0x90` with velocity 0, is note off; control change 64 (`0xB0`) is the sustain pedal (down at value ≥ 64), reported through `onSustain`. The main component keeps one `{ held, sustained, pedal }` per source (`"bt"`, or `"midi:<port id>"` for each Web MIDI input) in `pianoSources`: a key released while that source's pedal is down moves to `sustained` and still counts for the chord until the pedal goes up. The chord uses the union of all sources. To avoid stuck notes, only a source that goes away is cleared, through `onRelease`: the BLE controller calls it when its link is released, `useMIDI` when a port disappears. Plugging in another device leaves the held chord alone. Clicked keys are cleared when the virtual keyboard gets hidden. On the Piano screen, `ConnectionStatus` (below the tabs in `.app-header`; in short landscape `.top-bar` becomes `display: contents` so tabs, status and gear share one row; the status there is a lighter rounded pill, smaller than the dark tab block and set off by a vertical line, so navigation and piano state read as two parts; on the explore screen `.app-header--explore::after` takes the status slot so the tabs keep the left half) shows the connected piano's name (Bluetooth icon and a "Déconnecter" button for direct BLE). When neither BLE nor Web MIDI is connected (including while Web MIDI is still `pending`, since its permission prompt may go unanswered), the connect screen (`ConnectScreen`, vertically centered) shows a title, two rounds of the same size side by side (`--connect-round`): the Bluetooth button (or "Reconnecter <name>" plus "Connecter un autre piano" when a device is known) and `UsbButton` (USB trident `UsbIcon`, which only opens the USB explanation, with the "Autoriser le câble USB" button while Web MIDI is `prompt`; amber when MIDI is `denied`/`unsupported`), then "Pas de piano connecté ? 👇" (the hand is `aria-hidden`, the label is the button's `aria-describedby`) above `VirtualPianoButton` (an octave drawn by `MiniKeysIcon`, label below; the dictionary is only reached through its tab). The three home buttons share one style (dim green outline `--accent-line`, green icon, light label; full green and glow only on hover or while the USB popup is open), because full green means "selected" elsewhere. Without Web Bluetooth, the Bluetooth round is replaced by the "Bluetooth non disponible" message. A cancelled picker shows no message, only a small ⓘ on the Bluetooth round (`bt-connect-hint`) opening "Votre piano n'apparaît pas ?".

**Chord detection (`identifyChords`).** This is a pure function over MIDI note numbers:
- Templates are written as degrees (`degrees: ["1", "3", "5", "♭7", "9"]`), from which `buildTemplate` derives the pitch-class `intervals`, the `required` ones, `degreeByInterval` and the explorer `voicing` (9, 11, 13 above the octave). The degree label is also the interval shown in the note table, so detection and the dictionary show the same labels (`9`, `♯9`, `𝄫7`).
- It reduces notes to pitch classes and tries each of the 12 roots against every entry in `CHORD_TEMPLATES`.
- Matching: every degree not listed in the template's `optional` must be present, and no pitch class outside the template is allowed. `optional` holds the perfect fifth of added-note chords (`6/9`, `m6/9`, `add9`, `madd9`) and of 7th-and-beyond chords (sus ones included), the 9th of `m11`, and the 9th/11th of 13ths. Triads, `6` and `m6` stay fully strict, and an altered fifth (♭5, ♯5) is never optional. `7♭13` keeps its fifth required: without it, it has the same keys as `7♯5`. The 9th stays required in `11` and `maj11`: making it optional made `X11` (3rd and 11th clashing) beat root-position m13 readings. `identifyChords(notes, accidentals, { allowIncomplete })` makes every degree required when `allowIncomplete` is false (the "Accords incomplets" setting).
- Optional degrees that weren't played are still listed in `noteIntervalPairs` with `missing: true`, inserted right after the degree that precedes them in the template (G7 without D: G B (D) F). `ChordCard` dims them and draws tall parentheses over the column; the table cells are placed explicitly (`gridColumn`/`gridRow`) so the parenthesis overlay can span both rows.
- The lowest sounding note gives slash-chord notation (`C/E`) when it differs from the root. Root and bass of the symbol are both named by `spellPc` from the setting (see Accidentals), so the bass reads as the key played (`E/A♭` with flats), even when the note table spells it differently (G♯).
- Results are sorted by priority: `SUFFIX_RANK` (how common the chord is) + 1.5 for an inversion + 1 per missing optional note, then alphabetically. They are deduplicated by `chordName` and capped at 4. The first result is shown as the primary card and the rest as "Autres possibilités".
- When notes are held but nothing matches (including a single note), a placeholder card is built with `buildPendingNotePairs`: one dot per pressed key replaces the chord name, and the note table still lists the notes.
- In short landscape the primary card's height comes from the screen, not its content: it is a size container (`container-type: size`) and the chord name is sized in `cqh` with tighter gaps (even tighter under 340 px high), so it fits without scrolling. Keep some slack when adding content to it.
- Display hold: the cards render `shown`, not the live result. Only the change from a recognized chord to no chord (placeholder or no key at all) is delayed: the chord (`held`) stays for `DISPLAY_HOLD_MS` (250 ms, restarted on each change) before switching. Every other change (chord → chord, no chord → chord, no chord → no chord) is shown at once. The keyboard labels and `ChordAnnouncer` use the live result.
- `ChordAnnouncer` keeps an always-present, visually hidden `role="status"` region announcing the primary chord (`Cm, Mineur`) or "Accord non reconnu" on the Piano screen, 400 ms after the last change so intermediate chords aren't read.
- Results carry spelled notes, not display text: `root`, `bass` and each `noteIntervalPairs` entry's `note` are `{ letter, alter }` (letter 0–6 = C…B, alter −2…+2), alongside `rootPc`/`bassPc`/`pc`. `chordName` (English symbols) is only used as the dedup key. The UI names notes and chord types through `useI18n()`.

**Internationalization (`src/i18n.js`).** No library. `createI18n(language, accidentals)` returns the display helpers, provided to every component by `I18nContext` (read them with `useI18n()`):
- `t(key)`: UI strings from `MESSAGES` (flat dotted keys such as `"midi.connected"`). A key missing in a language falls back to French. Add every new key to all four languages.
- `chordTypeName(suffix)` and `groupName(id)`: chord type and dictionary group names, keyed by template `suffix` and group `id` from `chords.js` (the templates hold no display text).
- `noteName(note)` names a spelled note, `pcName(pc)` a key outside any chord (sharps or flats from the setting), and `keyLabel(midi)` adds the octave. Note names follow the language's convention (Do Ré Mi in French, Do Re Mi in Spanish, C D E in English, C D E … A B H in German, where H is B natural and B is B♭). Octave numbers: middle C (MIDI 60) is Do3 in French and Spanish, C4 in English and German.
- `rootName(note)`: root and bass of chord symbols (spelled notes). Symbols use English letters in every language except German, which uses H/B so that symbols match the note table (`Hmaj7`, not `Bmaj7`).
- `inversionLabel(i)`: "1er renversement", "1st inversion", and so on.

French stays the default (`DEFAULT_LANGUAGE`, no browser-language detection). The main component also sets `<html lang>` to the chosen language.

**Accidentals and spelling.** They are always the real symbols ♯ ♭ 𝄪 𝄫 (never ASCII `#` or `b`), in note names, chord suffixes (`7♯5`, `m7♭5`) and degrees (`𝄫7`); `ACCIDENTAL_SYMBOLS` in `chords.js` holds them. Their fallback font is taller than Oswald/JetBrains Mono, so `ChordCard` wraps them with `withAccidentals` in a `.chord-acc` span with `line-height: 0`: a flat must not make the card taller and shift the buttons below. The `accidentals` setting (`"sharp"` | `"flat"`, default `DEFAULT_ACCIDENTALS`) names every black key through `spellPc`: chord roots and slash basses (so a symbol is all sharps, C♯ D♯ F♯ G♯ A♯, or all flats, D♭ E♭ G♭ A♭ B♭, apart from suffix alterations like `7♭9`), explorer root chips, keyboard labels and unrecognized notes. Chord tones are then spelled exactly from the root: `spellDegree` gives each one the letter of its degree (Fm = F A♭ C, Eaug = E G♯ B♯, D♯ = D♯ F𝄪 A♯, G♭m = G♭ B𝄫 D♭).

**Settings.** The gear button opens `SettingsDialog`, a native `<dialog>` (Escape or a backdrop click closes it). It holds the language (flags), sharps/flats (two joined buttons, with an ⓘ explaining that chord tones keep their exact spelling whatever the setting), sound (with an ⓘ crediting the piano samples) and incomplete chords (on/off `Switch`, both on by default). Below a separator it shows the app version, which `vite.config.js` injects from `package.json` as `import.meta.env.VITE_APP_VERSION`, the author `cestymour` linked to the GitHub repo, and the MIT license (`LICENSE`).

**Short texts, details behind ⓘ.** The UI keeps visible text short. A longer explanation goes behind a circled-i `InfoButton`, and opens as a `Popup`: on the connect screen (USB, Bluetooth messages through `InfoTip`, the cancelled-picker ⓘ through `PopupInfoButton`) and in the settings (`PopupInfoButton`). `usePopupZone` gives each screen its `PopupContext` value and a `.popup-zone`, floating at the top of the screen (or of the settings dialog) outside the layout flow, into which popups are portaled, so opening one never moves anything (centered on screen in short landscape). Only one is open at a time; a tap outside it (and outside its button) or Escape closes it. In the settings, Escape closes the open popup first (the keydown is `preventDefault`ed and `onCancel` is cancelled), and only then the dialog. Each Bluetooth message has a short key (`bt.lost`, `bt.error.<code>`, `bt.unsupported`) and its detail under `<key>.help`. All four are saved in `localStorage` (`instantchordbt.language`, `instantchordbt.accidentals`, `instantchordbt.sound`, `instantchordbt.incomplete`) by `usePersistentSetting`, so they are restored on the next launch.

**Explorer voicings.** The voicing stacks all of a template's degrees, optional ones included, with extensions above the octave (9 → 14, 11 → 17, 13 → 21). `buildChordVoicing` puts the bass in [48, 59]. Inversion k rotates that stack: the k-th degree goes to the bass, and every following degree (then the earlier ones) is placed just above the previous note (Dm9: D F A C E, F A C E D, A C E D F, C E D F A, E D F A C). So the cycle always comes back to the root-position voicing. Don't sort-and-raise the lowest note instead: with 9ths and beyond, that reshuffles the stack and the cycle never returns. The bass-to-top span never exceeds 22 semitones (fits in 48–81). Round trip `identifyChords(voicing)` always lists the chosen chord, and in root position it comes first (except `aug7`, which ties with `7♯5`). Inversions may come out under another name when chords share notes: aug, dim7, sus2/sus4, 6/m7, m6/m7♭5, 6/9 / 9sus4, 13ths.

**Chord table notes.** `SUFFIX_RANK` keys must match template suffixes exactly; a missing key silently falls back to rank 6. `aug7` and `7♯5` have identical intervals, so both always match together (intentional: several chord names can share the same keys).
