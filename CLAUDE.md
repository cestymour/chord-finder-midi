# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

InstantChordBT: a React 19 + Vite PWA that identifies the chord being played on a MIDI keyboard, connected either by cable/OS-level MIDI (Web MIDI API) or directly over Bluetooth LE (Web Bluetooth API). Plain JavaScript (no TypeScript), Vitest unit tests, no router, no state library. The UI is available in English (default), French, German, Spanish, Portuguese, Chinese (simplified), Japanese and Korean; most code comments are in French.

## Commands

```bash
npm install        # .npmrc sets legacy-peer-deps=true (added so the CI npm install succeeds)
npm run dev        # Vite dev server, served at base "/"
npm run build      # Production build to dist/, base "/chord-finder-midi/"
npm run preview    # Serve the production build
npm run lint       # ESLint (flat config, eslint.config.js)
npm test           # Vitest unit tests (src/*.test.js), also run by CI before the build
npx vitest run src/chords.test.js   # a single test file
node scripts/sim-analyze.mjs [logs/sim-….json] [--engines A1,A2,A3,A4,A5] [--detail]   # replay a mic simulation recording (see Microphone simulation mode)
```

Tests cover the React-free modules: `micChroma.js`, `micBasicPitch.js` and `micTracker.js` (microphone mode, on synthetic piano-like signals from `src/micSynth.js`: single notes give one pitch class, chords and inversions round-trip through `identifyChords`, plus the rules of each engine A version and the tracker's attack gate and release; `micBasicPitch.test.js` also runs the real Basic Pitch model on TensorFlow.js's CPU backend, about 2 s per analysis, plus resampling and the capture ring buffer of `micCapture.js`), `simRecorder.js` (WAV encoding, file names, journal), `chords.js` (spelling, detection rules, and a round trip over every template × 12 roots × every inversion, with and without incomplete chords), `score.js` (written octaves, missing-note placement, clef choice), `i18n.js` (every key and chord type in every language, note-name conventions), `midiMessages.js`, `explorerLayout.js` (every template placed exactly once), the BLE packet decoding and error codes of `useBluetoothMIDI.js`, and the sample mapping of `pianoSound.js`. React components and the Bluetooth connection flow are not unit-tested. Run with Node 24 (`.nvmrc`). Web MIDI and Web Bluetooth only work in Chromium-based browsers and need a secure context (localhost or HTTPS).

## Deployment

Pushing to `main` triggers `.github/workflows/deploy.yml`, which builds with the Node version from `.nvmrc` (24) and deploys `dist/` to GitHub Pages. The service worker (vite-plugin-pwa, `generateSW`) precaches the app shell, and `workbox.runtimeCaching` caches the Google Fonts (imported at the top of `App.css`) for offline use. The `base` path in `vite.config.js` switches on `NODE_ENV` (`/chord-finder-midi/` in production), and the PWA manifest `scope`/`start_url` reuse it, so renaming the repo means updating that value. The PWA manifest (name, icons, theme colors) is also defined in `vite.config.js`; icon files live in `public/`. Two SVG sources: `favicon.svg` (5 keys, C-E-G lit; the browser tab, also rendered into `favicon.ico` at 16/32/48 px) and `logo.svg` (the three lit keys joined by a bar, rising to a dot; rendered into `apple-touch-icon.png` and `pwa-192x192.png`/`pwa-512x512.png`, which is also the maskable icon). Their background fills the whole square (no frame drawn inside: the OS applies its own mask). ffmpeg can't read SVG here; render the PNGs with headless Edge (`--screenshot`) and crop them with ffmpeg.

## Architecture

UI, hooks and components are in `src/App.jsx`. The chord engine (templates, detection, explorer voicings) is a pure, React-free module in `src/chords.js`, so it can be imported from plain Node for quick checks. All translations live in `src/i18n.js` (it imports `./chords.js` with the extension so it can be loaded from Node too). The BLE transport is in `src/useBluetoothMIDI.js`. The piano sound is in `src/pianoSound.js`: Salamander Grand Piano samples (Alexander Holm, CC-BY 3.0, credited behind the ⓘ of the Sound setting, `settings.soundHint` plus a link `PIANO_SAMPLES_URL`, and in the README) in `public/piano/<midi>.mp3`, one every 3 semitones from 21 to 108 (mono, 48 kb/s, shortened to 3–6 s with a fade), each note played from the nearest sample with `playbackRate` (at most ±1 semitone). `setPianoSoundEnabled(true)` (on launch when sound is on) fetches and decodes them through an `OfflineAudioContext`, so no user gesture is needed; a note whose sample isn't decoded yet stays silent (its key still lights up). There is no synthesized fallback. The service worker precaches the samples (`workbox.globPatterns` includes `mp3`). To regenerate them, re-encode the Salamander files with ffmpeg (`-ac 1 -b:a 48k`, trim + fade). Playback: the virtual keyboard plays a note when a key goes down and damps it when it goes up, the dictionary plays each chosen chord as an arpeggio (`playPianoArpeggio`), except that tapping the same chord again (same root, type and inversion) alternates block chord (`playPianoChord`) on even taps and arpeggio on odd ones (`exploreRepeatRef` counts consecutive taps), and notes from the real piano are never synthesized (the real piano is heard).

**Note input: three parallel sources feeding the same state.** `ChordIdentifier` (the main component) owns a `Set` of pressed MIDI note numbers and exposes `handleNoteOn`/`handleNoteOff`. Both input hooks call them:
- `useMIDI` (in `App.jsx`) uses `navigator.requestMIDIAccess`, attaches `onmidimessage` to every connected input except virtual "Through" ports, and re-attaches on `onstatechange`. It only requests access on its own when `navigator.permissions.query({ name: "midi" })` says `granted` (it follows `onchange`); otherwise the status is `prompt` and `requestAccess()` (the "Autoriser le câble USB" button in the USB popup of the connect screen) asks on a user gesture. A dismissed prompt goes back to `prompt`, a refusal to `denied`. It returns `{ status, devices, requestAccess }`: status is `pending | prompt | connected | disconnected | denied | unsupported`, devices the input names. This covers USB pianos (on Android through a USB OTG adapter) and Bluetooth pianos paired at OS level; Web MIDI can't tell the two apart.
- `useBluetoothMIDI` connects to the standard BLE MIDI service/characteristic UUIDs, subscribes to notifications, and decodes packets with `ble-midi-parser`. This direct decoding exists because some platforms (notably Windows Chrome) don't expose a BLE MIDI device as a Web MIDI port. The logic lives in a React-free `createBluetoothController`; every action bumps `ctx.attempt` so stale async work gives up. Statuses: `idle | scanning | connecting | connected | reconnecting | lost | error | unsupported`. `ctx.target` is the device currently wanted: a superseded `openLink` closes GATT unless the newer action targets the same device, and a failed open closes it too, so the piano is never left connected with nobody listening. An unrequested GATT disconnect starts an automatic reconnect on the same device (about 20 s, then `lost`). The last device stays known (`btKnownDevice`) after a loss or a manual disconnect, so `reconnectBluetooth` reconnects without the picker. Its id is saved in `localStorage` (`instantchordbt.bluetoothDevice`), and on launch `navigator.bluetooth.getDevices()`, where available, restores it. Such a restored device (`ctx.restored`, until its first successful connection) often refuses `gatt.connect()` until the browser has seen it advertise: only when that first open fails, `connect` waits up to 10 s for an `advertisementreceived` event (`watchAdvertisements`, aborted by any newer action) and retries once. The normal path is unchanged. `btError` is a code (`cancelled | adapterOff | denied | failed`) translated as `bt.error.<code>`. A cancelled picker is shown as a hint, not an error.
- `useMicrophone` (`src/useMicrophone.js`, experimental) listens to an acoustic piano. `startMic(engine)` (one of `MIC_ENGINES`: only `"A5"` (`MIC_DEFAULT_ENGINE`) in production; `"A1"`–`"A5"` and `"B1"` under `npm run dev`; kept in `micEngine`) must run on a user gesture: it creates the `AudioContext` first, then `getUserMedia` with `echoCancellation`, `noiseSuppression` and `autoGainControl` off, then prepares the engine, then starts `startCapture` (`src/micCapture.js`: an AudioWorklet loaded from a Blob URL, or a ScriptProcessorNode where worklets are missing, both routed to a muted gain so every browser runs them, posting blocks of 1024 samples into a 2.5 s ring buffer, `createRingBuffer`). Every 50 ms (`setInterval`) the hook sends the meter level of the last 2048 samples, then, unless the engine is still busy or ran less than `engine.minIntervalMs` ago, awaits `engine.analyze` on the latest `engine.frameSize` samples (engines may be async). Engine B (`createBasicPitchEngine` in `src/micBasicPitch.js`, pure; the model is injected) resamples the last 2 s to 22 050 Hz (`resampleTail`, windowed sinc from a precomputed polyphase table, about 7 ms), runs Spotify's Basic Pitch model (`public/models/basic-pitch/`, Apache 2.0, 172 frames × 88 keys of note probabilities), skips the last `EDGE_FRAMES` (15) frames where the network lacks context, and takes each key's maximum over the `READ_FRAMES` (12) before (`recentNotes`); saliences are absolute probabilities, so its tracker thresholds are `BASIC_PITCH_TRACKER` (0.45 on / 0.3 off). `src/micBasicPitchModel.js` imports TensorFlow.js (`tfjs-core`, `tfjs-converter`, WebGL backend with CPU fallback) and loads the model once, with a warm-up run; it is only reached through a dynamic import, so it is a separate chunk (~800 KB) that the service worker does not precache: `globIgnores` skips it and `runtimeCaching` keeps it (and the model files) after the first use of "Micro B". A load failure gives `micError` `"model"`. Engine A (`createChromaEngine({ sampleRate, version = CHROMA_LATEST })` in `src/micChroma.js`, pure) returns `{ notes: [{ midi, salience }], level, recentLevel, tuning, classEnergy }`: Hann window and FFT (`frameSpectra`: peaks up to 300 Hz from the whole ~340 ms frame, above from its most recent half), parabolic peak interpolation, global tuning offset (circular mean, smoothed), then iterative multi-pitch estimation (`detectNotes`: harmonic sum with inharmonicity allowance; the winner's partials are subtracted, at most down to the smoothed level of its neighbours; a candidate needs its fundamental; `pruneHarmonicGhosts` drops weak notes exactly on the 3rd, 5th, 6th or 7th harmonic of a lower note). The versions stack rules, and the older ones stay selectable for comparison until the field tests are done (`detectNotes` options `octaveFix`, `lowSupport`, `lowOctaveGhost`, `lowOctave`, `maxMidi`; `rules` overrides them):
  - A1: the original engine, MIDI 36–88, fundamental at least 5 % of the strongest partial.
  - A2: adds `classEnergy` (12 values, each pitch class's strongest harmonic sum read straight from the spectrum, not from peaks, so a steady sound gives a steady value), used by the tracker's attack gate.
  - A3 (`octaveFix`, octave errors): the required fundamental (`minFundamental`) rises from 5 % below C3 (130.8 Hz) to 25 % one octave higher, since a phone mic picks up low fundamentals poorly but a piano always has a clear one above; a weak note one or two octaves below a stronger one of the same name is pruned from MIDI 48 up.
  - A4 (`lowSupport`): below 300 Hz a note needs one of its harmonics 2–4 at ≥ 5 % of its strongest partial, and when that support only comes from fundamentals of notes already found (`claimed`), its own fundamental must reach 25 %; below MIDI 48 an octave ghost is also pruned when under 15 % of the upper note (`lowOctaveGhost`). The range goes up to MIDI 108 (`MIC_MAX_MIDI_HIGH`), and its tracker settings are `{ attackFrames: 10, releaseDb: 12 }` (`engine.tracker`).
  - A5 (`lowOctave`, the default and the only production engine): below C3 a note needs its octave (raw peak) at ≥ 2 % of its fundamental, which removes fixed low resonances (cabinet, room, speakers: about 73, 105 and 140 Hz on the digital piano used for tuning) that otherwise became a ghost bass by collecting the played notes as harmonics 6–8.
  `createNoteTracker` (`src/micTracker.js`, pure, shared by all engines, settings from `engine.tracker` over `DEFAULTS`) folds notes into pitch classes keeping each class's lowest note, applies on/off salience hysteresis (0.15 / 0.08 by default) and a level gate (−50 dB to start, −58 dB to stop), and only changes its output when the same reading (classes + bass class) comes back on 2 consecutive frames, or at once when analyses are more than `slowFrameMs` (300 ms) apart (slow device running engine B); silence releases at once. When the engine gives `classEnergy` (A2 and later), two more rules apply. Attack gate: a class not yet held may only enter when its energy is at least `attackRatio` (2, +6 dB) times the lowest of its last `attackFrames` frames (6 by default, 10 for A4+), because a piano note always starts with a hammer strike; otherwise, as a chord decays, leftover resonance becomes "the loudest" and would pass the relative thresholds. Release: with `releaseDb` (A4+), when `recentLevel` (the last 2048 samples, ~45 ms) falls at least that many dB below the highest of the last `releaseFrames` (3) frames, every held class is released at once (dampers cut the whole chord together, so the relative weights don't change); `releaseDrop` (per-class energy drop, off by default) does the same per class. A released class only comes back with a new attack, at least `attackRatio` times its energy at release (`blocked`). The hook diffs the output into `onNoteOn`/`onNoteOff` for source `"mic"` (no pedal), and calls `onRelease` when it stops. Statuses: `idle | starting | listening | error | unsupported`; `micError` is `denied | noDevice | failed` (translated as `mic.error.<code>`), and a site permission already `denied` (`permissions.query({ name: "microphone" })`) shows as that error up front; a granted permission never starts listening on its own. `subscribeLevel` feeds the `MicLevel` meter without React renders, with the duration of the last analysis shown next to it under `npm run dev` (`mic.computeTime`); the status reads "Micro", followed under `npm run dev` by one button per engine to switch. While listening on the Piano screen, the app's piano sound is off (`setPianoSoundEnabled(sound === "on" && !micMutes)`) so it is not picked up. `suppress()` (called on every virtual-key tap) turns the heard notes off and keeps the mic silent while it only hears those pitch classes (their resonance); a new pitch class or silence lifts it, so a tap works like on a real piano. There is no engine setting: the home screen has a single "Micro" round (engine A5) with an ⓘ (`mic.help`); `mic.engineA`/`mic.engineB` are the titles of the dev-only switch buttons (`switchMic` sets `micSwitching`, so the Piano screen stays up while the new engine starts; `goHome` and `choose` clear it).
- **Microphone simulation mode** (dev server only, for tuning the engines without an acoustic piano): plug in a digital piano (USB or Bluetooth) and start the mic so it hears the piano's speakers. `simActive` (`import.meta.env.DEV && micListening && pianoConnected`) then shows only the mic's notes (`pressedNotes` skips the other sources); the MIDI keys are the ground truth. `ConnectionStatus` shows a `SIM` badge and "● Enregistrer" / "■ Stop" (French-only text, dev-only). A recording (`createSimRecording` in `src/simRecorder.js`, held in `simRef`) takes the mic audio through `mic.listenAudio` (`capture.listen` in `micCapture.js`, a copy of each block) and logs timestamped events: `midiOn` (with velocity, which `dispatchMidiMessage` now passes as the second argument of `onNoteOn`), `midiOff`, `pedal`, `micOn`/`micOff`, every engine output (`frame`, through the `onFrame` callback of `useMicrophone`, before the tracker), the starting state (`midiState`, `micState`), and `audioMarks` aligning samples with the clock. Stopping, stopping the mic or switching engines (`listenAudio` listeners get `null` on teardown) saves `logs/sim-AAAAMMJJ-HHMMSS-<engine>.wav` (mono 16-bit, `encodeWav`) and `.json` through `saveSimFile`, a POST to `/__sim/save`, served by the `simulationLogs` plugin of `vite.config.js` (`configureServer`, so dev only; names must match `^[\w.-]+\.(wav|json)$`; `logs/` is git-ignored). `scripts/sim-analyze.mjs` replays a recording (the latest by default) through any engine versions at the same analysis instants as the live session, and scores each chord played against the MIDI truth (same pitch classes and same bass): `--engines`, `--detail`, `--tracker '{…}'` and `--rules '{…}'` try other settings. Everything here (old A versions, B, switch buttons, simulation mode, compute time) is to be removed once the field tests are done (see `TODO.md`).

**Screens.** `mode` is `"midi"` (tab "Notes → Accord") or `"explore"` (tab "Accord → Notes"), chosen in the segmented `TopBar` (exactly one tab is always active). The arrow labels name the direction so they make sense without context; each tab also has a spelled-out `aria-label` (`tabs.<key>.aria`) so screen readers don't read "right arrow". The app always starts on Piano: connecting a real piano is the app's main purpose. The on-screen keyboard is a fallback, so it stays hidden until it is needed.
- `"midi"` (the Piano screen, tab "Notes → Accord"): the real piano and the on-screen `VirtualKeyboard` share this screen. The keyboard shows only when a piano is connected (BLE or Web MIDI, including while BLE is `reconnecting`, so a short drop doesn't bring the connect screen back, or the microphone is listening) and the user hasn't asked for home (`homeRequested`), or after the user taps "Piano virtuel" on the connect screen (`keyboardChosen`, not saved). The keyboard keeps its own `virtualNotes` set (click toggles a key), so hardware note-offs can't release clicked keys. The chord is computed from the union of piano and clicked notes, and a piano note-on clears the clicked keys so the two sources don't mix. The keyboard lights both, and scrolls to the piano notes only. When the keyboard was chosen without a piano, `ConnectionStatus` shows a neutral "Piano virtuel" state (never a MIDI error). Whatever the source, while the Piano screen is shown `ConnectionStatus` has one "Retour" button (`BackIcon`, `status.back`): `goHome` stops the mic, disconnects direct BLE, clears `keyboardChosen` and sets `homeRequested` (needed because a Web MIDI piano can't be disconnected). Any choice on the home screen (`choose(...)`), a note from a Web MIDI source, or tapping the USB round while Web MIDI is connected (it then shows the device name and goes straight to the Piano screen) clears `homeRequested`. `virtualNotesRef` is updated together with the state on every change, so quick taps before a render each start from the latest set.
- `"explore"` (the dictionary, tab "Accord → Notes"): the reverse direction. The compact chord card and the root chips (no title, `aria-label` only; 2 rows of 6) stay at the top (in short landscape, card then roots in the left column and the chord types alone in the right one: `.display-area--explore` becomes a grid and `.explorer` `display: contents`); all chips are at least 36 px high and have the home buttons' dim turquoise outline (`--accent-line`); in portrait `.display-area--explore` tightens the space around the chord card; root chips use 1.2rem, type chips stay 0.7rem; only `.explorer__scroll` (the chord types) scrolls, in portrait and in short landscape. The types are two aligned 6-column grids defined in `src/explorerLayout.js`: `MATRIX_ROWS` (quality rows such as M, add, m, dom, sus4, dim, aug, no3 × highest extension: triad, 6, 7, 9, 11, 13, headers translated with `explorer.triad` and the ordinal pattern `explorer.nth`), and `ALTERED_ROWS` (base 7th chord × alteration ♭5 ♯5 ♭9 ♯9 ♯11 ♭13), in a `<details>` closed by default unless the chosen chord is altered. Every template suffix sits in exactly one cell (checked by `explorerLayout.test.js`), so a new template in `chords.js` must also be placed there. Buttons show the suffix only (`M` for the empty major suffix, full type name in `aria-label`/`title`); empty cells are a small dot. `ChordExplorer` picks a root and a template; `buildChordVoicing` turns it into concrete keys, shown read-only on the keyboard (only the voicing keys are lit). "Renverser" cycles inversions (see Explorer voicings).

**Desktop layout.** Everything for computers lives in one block at the end of `App.css`, under `@media (min-width: 900px) and (min-height: 561px)` (`DESKTOP_QUERY` in `App.jsx` must match it), so phones in portrait and in short landscape are untouched. The app is as wide as the full keyboard (52 white keys × 24 px, `--desk-kb-width`), and the keyboard is shown whole and centered (it scrolls only in a narrower window). Above it, the portrait layout sits in a centered 960 px column (`--desk-col`, applied as `padding-inline` so backgrounds stay full width; a `.top-bar::before` spacer as wide as the gear (48 px) centers the tabs, so their split lines up with the halves below). The primary card takes the left half and the alternatives the right half; with no alternatives the card is centered (`:not(:has(> .secondary-chords))`). On the explore screen `.display-area--explore` is a grid and `.explorer` is `display: contents`: chord card | roots (2 rows of 6) on top, then both type grids side by side, equal width and aligned with the card and roots above (same 20 px gap, divider in its middle), the only part that scrolls. The altered grid is always open there (`ChordExplorer` forces `open` through `useMediaQuery(DESKTOP_QUERY)`, its summary is hidden), and each grid gets a title (`.explorer-grid-title`, hidden on mobile): `explorer.main` (« Classiques ») and `explorer.altered`.

**Virtual keyboard.** A full 88-key piano (MIDI 21–108) inside a horizontal scroller. The key track width is set from `--vk-white-keys` (52) so that 14 white keys (2 octaves) are visible in portrait and 21 (3 octaves) in landscape on desktop. On a phone on its side (short landscape) the white key keeps its portrait width (`(100vh - 24px) / 14`, clamped 22–32 px), so more keys show instead of wider ones. On mount it scrolls instantly so MIDI 48 is at the left. Key positions are percentages from `VK_KEY_SPANS`. `useScrollIntoView` smooth-scrolls (respecting `prefers-reduced-motion`) to put the lowest note at the left only when part of the given notes is hidden: the explorer voicing, or the notes played on the piano (high notes of a wide chord may stay hidden). Notes outside the 88 keys are ignored.

Both hooks decode MIDI with the shared `dispatchMidiMessage` (`src/midiMessages.js`): `0x90` with velocity > 0 is note on (`onNoteOn(note, velocity)`; only the simulation log uses the velocity); `0x80`, or `0x90` with velocity 0, is note off; control change 64 (`0xB0`) is the sustain pedal (down at value ≥ 64), reported through `onSustain`. The main component keeps one `{ held, sustained, pedal }` per source (`"bt"`, `"mic"`, or `"midi:<port id>"` for each Web MIDI input) in `pianoSources`: a key released while that source's pedal is down moves to `sustained` and still counts for the chord until the pedal goes up. The chord uses the union of all sources. To avoid stuck notes, only a source that goes away is cleared, through `onRelease`: the BLE controller calls it when its link is released, `useMIDI` when a port disappears, `useMicrophone` when listening stops. Plugging in another device leaves the held chord alone. Clicked keys are cleared when the virtual keyboard gets hidden. On the Piano screen, `ConnectionStatus` (below the tabs in `.app-header`; in short landscape `.top-bar` becomes `display: contents` so tabs, status and gear share one row; the status there is a lighter rounded pill, smaller than the tab buttons and set off by a vertical line, so navigation and piano state read as two parts; on the explore screen `.app-header--explore::after` takes the status slot so the tabs keep the left half) shows the connected piano's name (Bluetooth icon for direct BLE), or, first of all while the microphone listens, "Micro" with the `MicLevel` meter, then the "Retour" button. The tabs (46 px high, 38 px in short landscape) show a drawn icon ("Notes → Accord" uses `KeysTabIcon`: lit keys; "Accord → Notes" uses `ChordTabIcon`: a chord on a staff; hidden under 420 px wide, so the label always fits on one line; the two tabs and the gear are three separate outlined buttons at the same level (`.mode-tabs` only groups the tabs for `role="tablist"`, with no background or border), and the gear stretches to the tabs' height and takes the active-tab look (`settings-btn--active`, `aria-expanded`) while `SettingsDialog` is open) and the label in the system sans-serif font, not uppercase. When neither BLE nor Web MIDI is connected nor the microphone listening (including while Web MIDI is still `pending`, since its permission prompt may go unanswered), the connect screen (`ConnectScreen`, vertically centered; also shown when `homeRequested`) has three `.connect-section`s, each a title above its buttons (stacked in portrait and on desktop, side by side in short landscape): "Connectez votre piano" (`connect.title`) with two rounds of the same size (`--connect-round`, sized from both width and height so everything fits a phone): the Bluetooth button (or "Reconnecter <name>" plus "Connecter un autre piano" when a device is known) and `UsbButton` (USB trident `UsbIcon`, which only opens the USB explanation, with the "Autoriser le câble USB" button while Web MIDI is `prompt`; amber when MIDI is `denied`/`unsupported`); "Écoutez votre piano" (`connect.listen`) with `MicButton` (`MicIcon`, reuses the `.usb-btn` styles; starts listening on tap with `MIC_DEFAULT_ENGINE`, reads "Démarrage…" while starting, with an ⓘ badge for `mic.help`; amber on error, with a short `mic.*` message and its ⓘ below the round); "Piano virtuel" (`fallback.keyboard`) above `VirtualPianoButton` (an octave drawn by `MiniKeysIcon` filling the whole button, `aria-label` only; the dictionary is only reached through its tab). The home buttons share one style (dim turquoise outline `--accent-line`, turquoise icon, light label; full turquoise and glow only on hover or while the USB popup is open), because full turquoise means "selected" elsewhere. Without Web Bluetooth, the Bluetooth round is replaced by the "Bluetooth non disponible" message. A cancelled picker shows no message, only a small ⓘ on the Bluetooth round (`bt-connect-hint`) opening "Votre piano n'apparaît pas ?".

**Chord detection (`identifyChords`).** This is a pure function over MIDI note numbers:
- Templates are written as degrees (`degrees: ["1", "3", "5", "♭7", "9"]`), from which `buildTemplate` derives the pitch-class `intervals`, the `required` ones, `degreeByInterval` and the explorer `voicing` (9, 11, 13 above the octave). The degree label is also the interval shown in the note table, so detection and the dictionary show the same labels (`9`, `♯9`, `𝄫7`).
- It reduces notes to pitch classes and tries each of the 12 roots against every entry in `CHORD_TEMPLATES`.
- Matching: every degree not listed in the template's `optional` must be present, and no pitch class outside the template is allowed. `optional` holds the perfect fifth of added-note chords (`6/9`, `m6/9`, `add9`, `madd9`) and of 7th-and-beyond chords (sus ones included), the 9th of `m11`, and the 9th/11th of 13ths. Triads, `6` and `m6` stay fully strict, and an altered fifth (♭5, ♯5) is never optional. `7♭13` keeps its fifth required: without it, it has the same keys as `7♯5`. The 9th stays required in `11` and `maj11`: making it optional made `X11` (3rd and 11th clashing) beat root-position m13 readings. `identifyChords(notes, accidentals, { allowIncomplete })` makes every degree required when `allowIncomplete` is false (the "Accords incomplets" setting).
- Optional degrees that weren't played are still listed in `noteIntervalPairs` with `missing: true`, inserted right after the degree that precedes them in the template (G7 without D: G B (D) F). `ChordCard` dims them and draws tall parentheses over the column; the table cells are placed explicitly (`gridColumn`/`gridRow`) so the parenthesis overlay can span both rows.
- The lowest sounding note gives slash-chord notation (`C/E`) when it differs from the root. Root and bass of the symbol are both named by `spellPc` from the setting (see Accidentals), so the bass reads as the key played (`E/A♭` with flats), even when the note table spells it differently (G♯).
- Results are sorted by priority: `SUFFIX_RANK` (how common the chord is) + 1.5 for an inversion + 1 per missing optional note, then alphabetically. They are deduplicated by `chordName` and capped at 4. The first result is shown as the primary card and the rest as "Autres possibilités".
- When notes are held but nothing matches (including a single note), a placeholder card is built with `buildPendingNotePairs`: one dot per pressed key replaces the chord name, and the note table still lists the notes.
- Staff (`ChordScore`, right of the chord name in `.chord-card__head`): the shown notes on one or two staves, drawn with VexFlow. `src/score.js` (pure) builds the notes with `buildScoreNotes` (every played key, spelled like the note table; each missing optional degree added just above the lowest played root, an octave higher for 9/11/13, drawn in parentheses and dimmed) and picks the staves with `chooseStaves` (treble or bass when every note fits with at most 2 ledger lines, the one matching the chord's middle when both do; otherwise both staves split at middle C). `src/scoreRenderer.js` draws them: noteheads without stems are whole notes with the `/so` notehead (black oval), no time or key signature, no barlines; the SVG is sized in staff spaces (`--score-w`/`--score-h` × `--score-space`) so the staff spacing never changes between chords. Colors come from the CSS variables `--score-line`/`--score-note`/`--score-dim` of `.chord-score`. VexFlow (`vexflow/bravura`, ~720 KB with its font) is loaded on demand by `loadVexFlow` (separate chunk, precached), which waits for the Bravura font before the first drawing. The SVG is cropped to the glyphs' ink (`inkBox`: glyphs are SVG text, and `getBBox()` would give them Bravura's full line height, about 4 staff heights, so their extent comes from `measureText`; VexFlow's transparent hit rectangles, `opacity="0"`, are skipped, since with parentheses the chord's one spans the whole drawing). The staff lines are then cut just after the chord's ink (`STAVE_TAIL`), whatever width VexFlow gave the staff. The staff is not rendered in short landscape (`SHORT_LANDSCAPE_QUERY`). The explore card always shows it, short landscape included (smaller, `--score-space: 6px`), right-aligned against the table's divider: its head becomes a flex box (`space-between`) in the first grid column, a third of the card when there is room (`minmax(max-content, 1fr) minmax(0, 2fr)`), while the alternatives cards keep `.chord-card__head` as `display: contents`.
- In short landscape the primary card's height comes from the screen, not its content: it is a size container (`container-type: size`) and the chord name is sized in `cqh` with tighter gaps (even tighter under 340 px high), so it fits without scrolling. Keep some slack when adding content to it.
- Display hold: the cards render `shown`, not the live result. Only the change from a recognized chord to no chord (placeholder or no key at all) is delayed: the chord (`held`) stays for `DISPLAY_HOLD_MS` (250 ms, restarted on each change) before switching. Every other change (chord → chord, no chord → chord, no chord → no chord) is shown at once. The keyboard labels and `ChordAnnouncer` use the live result.
- `ChordAnnouncer` keeps an always-present, visually hidden `role="status"` region announcing the primary chord (`Cm, Mineur`) or "Accord non reconnu" on the Piano screen, 400 ms after the last change so intermediate chords aren't read.
- Results carry spelled notes, not display text: `root`, `bass` and each `noteIntervalPairs` entry's `note` are `{ letter, alter }` (letter 0–6 = C…B, alter −2…+2), alongside `rootPc`/`bassPc`/`pc`. `chordName` (English symbols) is only used as the dedup key. The UI names notes and chord types through `useI18n()`.

**Internationalization (`src/i18n.js`).** No library. `createI18n(language, accidentals)` returns the display helpers, provided to every component by `I18nContext` (read them with `useI18n()`):
- `t(key)`: UI strings from `MESSAGES` (flat dotted keys such as `"midi.connected"`). A key missing in a language falls back to English (`DEFAULT_LANGUAGE`). Add every new key to all eight languages.
- `chordTypeName(suffix)` and `groupName(id)`: chord type and dictionary group names, keyed by template `suffix` and group `id` from `chords.js` (the templates hold no display text).
- `noteName(note)` names a spelled note, `pcName(pc)` a key outside any chord (sharps or flats from the setting), and `keyLabel(midi)` adds the octave. Note names follow the language's convention (Do Ré Mi in French, Do Re Mi in Spanish, Dó Ré Mi in Portuguese, C D E in English, Chinese, Japanese and Korean, C D E … A B H in German, where H is B natural and B is B♭). Octave numbers: middle C (MIDI 60) is Do3 in French, Spanish and Portuguese, C4 in the other languages.
- `rootName(note)`: root and bass of chord symbols (spelled notes). Symbols use English letters in every language except German, which uses H/B so that symbols match the note table (`Hmaj7`, not `Bmaj7`).
- `inversionLabel(i)`: "1er renversement", "1st inversion", and so on.

English is the default (`DEFAULT_LANGUAGE`, no browser-language detection; `index.html` `lang` and the manifest description are in English too). The main component also sets `<html lang>` to the chosen language.

**Accidentals and spelling.** They are always the real symbols ♯ ♭ 𝄪 𝄫 (never ASCII `#` or `b`), in note names, chord suffixes (`7♯5`, `m7♭5`) and degrees (`𝄫7`); `ACCIDENTAL_SYMBOLS` in `chords.js` holds them. Their fallback font is taller than Oswald/JetBrains Mono, so `ChordCard` wraps them with `withAccidentals` in a `.chord-acc` span with `line-height: 0`: a flat must not make the card taller and shift the buttons below. The `accidentals` setting (`"sharp"` | `"flat"`, default `DEFAULT_ACCIDENTALS`) names every black key through `spellPc`: chord roots and slash basses (so a symbol is all sharps, C♯ D♯ F♯ G♯ A♯, or all flats, D♭ E♭ G♭ A♭ B♭, apart from suffix alterations like `7♭9`), explorer root chips, keyboard labels and unrecognized notes. Chord tones are then spelled exactly from the root: `spellDegree` gives each one the letter of its degree (Fm = F A♭ C, Eaug = E G♯ B♯, D♯ = D♯ F𝄪 A♯, G♭m = G♭ B𝄫 D♭).

**Settings.** The gear button opens `SettingsDialog`, a native `<dialog>` (Escape or a backdrop click closes it). It holds the language (8 flags in 2 rows of 4, drawn as inline SVG in `FLAGS` because flag emoji don't render on Windows), sharps/flats (two joined buttons, with an ⓘ explaining that chord tones keep their exact spelling whatever the setting), sound (with an ⓘ crediting the piano samples) and incomplete chords (on/off `Switch`, both on by default). Below a separator it shows the app version, which `vite.config.js` injects from `package.json` as `import.meta.env.VITE_APP_VERSION`, the author `cestymour` linked to the GitHub repo, and the MIT license (`LICENSE`).

**Short texts, details behind ⓘ.** The UI keeps visible text short. A longer explanation goes behind a circled-i `InfoButton`, and opens as a `Popup`: on the connect screen (USB, Bluetooth messages through `InfoTip`, the cancelled-picker ⓘ through `PopupInfoButton`) and in the settings (`PopupInfoButton`). `usePopupZone` gives each screen its `PopupContext` value and a `.popup-zone`, floating at the top of the screen (or of the settings dialog) outside the layout flow, into which popups are portaled, so opening one never moves anything (centered on screen in short landscape). Only one is open at a time; a tap outside it (and outside its button) or Escape closes it. In the settings, Escape closes the open popup first (the keydown is `preventDefault`ed and `onCancel` is cancelled), and only then the dialog. Each Bluetooth message has a short key (`bt.lost`, `bt.error.<code>`, `bt.unsupported`) and its detail under `<key>.help`. All four are saved in `localStorage` (`instantchordbt.language`, `instantchordbt.accidentals`, `instantchordbt.sound`, `instantchordbt.incomplete`) by `usePersistentSetting`, so they are restored on the next launch.

**Explorer voicings.** The voicing stacks all of a template's degrees, optional ones included, with extensions above the octave (9 → 14, 11 → 17, 13 → 21). `buildChordVoicing` puts the bass in [60, 71] (from middle C, Do3 in French). Inversion k rotates that stack: the k-th degree goes to the bass, and every following degree (then the earlier ones) is placed just above the previous note (Dm9: D F A C E, F A C E D, A C E D F, C E D F A, E D F A C). So the cycle always comes back to the root-position voicing. Don't sort-and-raise the lowest note instead: with 9ths and beyond, that reshuffles the stack and the cycle never returns. The bass-to-top span never exceeds 22 semitones (fits in 60–93). Round trip `identifyChords(voicing)` always lists the chosen chord, and in root position it comes first (except `aug7`, which ties with `7♯5`). Inversions may come out under another name when chords share notes: aug, dim7, sus2/sus4, 6/m7, m6/m7♭5, 6/9 / 9sus4, 13ths.

**Chord table notes.** `SUFFIX_RANK` keys must match template suffixes exactly; a missing key silently falls back to rank 6. `aug7` and `7♯5` have identical intervals, so both always match together (intentional: several chord names can share the same keys).
